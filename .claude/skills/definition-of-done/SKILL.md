# Definition of Done

## 이 스킬이 푸는 문제

AI는 "다 됐습니다"를 너무 쉽게 말한다. 판정 기준이 AI의 산문 속에만 있으면
모델마다, 세션마다 기준이 달라지고 검증은 인상 비평이 된다.

해결책은 더 좋은 문장이 아니라 **판정 권한을 모델에게서 뺏는 것**이다.
모델에 독립적인 것은 두 가지뿐이다.

1. 동결된 파일 — 사람이 diff로 변조를 감지할 수 있다
2. **이름 붙은 산출물의** exit code

두 번째에 "이름 붙은 산출물의"가 붙는 이유가 이 스킬의 핵심이다.
exit code 자체에는 해석의 여지가 없지만, **그것이 무엇을 재는지는 보장되지 않는다.**
계약서 안에 손으로 짠 셸 검사기는 그 자체가 검증된 적 없는 프로그램이고,
자기가 주장하는 것을 재지 않으면서 exit 0을 낸다.

## 절대 규칙

1. 계약서가 FROZEN 되기 전에 구현 코드를 쓰지 않는다.
2. 증거 없이 완료를 말하지 않는다. 증거는 방금 실행한 명령의 출력이다.
3. 동결된 기준을 조용히 고치지 않는다. 고치려면 멈추고 재승인받는다.
4. 사람 확인 대기가 1건이라도 있으면 "완료"라는 단어를 쓰지 않는다.

## 절차

### Gate 1 — 착수 (구현 전)

1. `docs/dod/<feature-slug>.dod.md`를 `template.dod.md` 기반으로 작성한다.
2. **기존 gate를 조사한다** (아래 "검증 수단" 참조). 조사 칸을 채운다.
3. 수용기준을 뽑는다. 개수는 기능이 요구하는 만큼이다.
4. 사람에게 제시하고 승인을 요청한다.
5. 승인되면 `status: FROZEN`과 `frozen_at`을 기입한다. 그 전에는 구현하지 않는다.

### 구현 중

- T1/T2 기준은 테스트를 먼저 쓰고 실패를 확인한다 (RED).
- RED 로그를 계약서 증거 로그에 붙인다.
- 구현 후 GREEN 로그를 붙인다.
- 기준이 틀렸음을 발견하면 구현을 멈추고 `## 변경 요청`을 추가한 뒤 재승인받는다.

### Gate 2 — 완료 판정

모든 기준에 증거가 있는지 확인하고 아래 고정 포맷으로 판정을 출력한다.

## 검증 수단

수용기준 표의 `검증 수단` 칸은 **식별자를 포함한** 다음 셋 중 하나다.

| 종류 | 식별자 형태 | 예 |
|---|---|---|
| `기존` | 저장소에 이미 있는 task·job 이름 | `./gradlew architectureTest` |
| `신규테스트` | 이번 변경으로 추가하는 테스트의 FQN | `io.x.LegacyNameArchitectureTest` |
| `신규스크립트` | 저장소에 커밋하는 실행 파일 경로 | `scripts/check-legacy-names.sh` |

**식별자를 적을 수 없으면 그 기준은 아직 T1도 T2도 아니다.**
Gate 1에서 사람에게 "셋 중 무엇을 만들 것인가"를 물어 결정한다.
**결정을 미루는 것이지 티어를 낮추는 것이 아니다.**

### 기존 gate 조사 (Gate 1 필수)

수용기준을 쓰기 전에 저장소가 이미 가진 검증 수단을 조사하고 계약서에 적는다.
architecture test, lint 규칙, custom gradle task, CI job을 실제로 찾아본다.
**이 칸이 비어 있으면 FROZEN으로 전이할 수 없다.**

이 조사를 건너뛰면 이미 있는 gate를 못 보고 셸 파이프라인을 새로 짜게 된다.

### T1 검증 명령의 형태

**이름 붙은 산출물 하나를 부르는 단일 명령이다.**

칸에 `|`, `&&`, `;`, `!`, `$(` 중 하나라도 있으면 그 기준은 T1이 아니다.
셸 조합은 그 자체가 검증되지 않은 프로그램이며, 조합의 exit code는
마지막 단계의 것이라 앞 단계의 실패를 삼킨다.

### 신규스크립트를 만들 때

그 스크립트는 계약서가 아니라 **저장소에 있고, 자기 수용기준을 갖는다.**
`## 검사 산출물` 표에 정상 표본과 위반 표본을 적고, 스크립트가 정상을 통과시키고
위반을 잡는지 먼저 증명한다. 그 증명 없이는 이 스크립트를 검증 수단으로 쓸 수 없다.

## 수용기준 작성 규칙

### 형태

`[조건]일 때 [주체]가 [관찰 가능한 결과]를 낸다`

### 판별 테스트

> 두 사람이 이 문장만 읽고 각자 판정했을 때 결과가 갈릴 수 있는가?

갈릴 수 있으면 실격이다. 다시 쓴다.

### 금지어

정상 동작 / 잘 처리 / 적절히 / 문제없이 / 안정적으로 /
사용자 친화적 / 빠르게 / 최적화 / 개선됨 / 견고하게

이 단어들은 관찰자마다 다르게 읽힌다. 등장하면 그 기준은 무효다.

### 개수와 완결성

**개수에는 상한도 하한도 없다.** 기능이 요구하는 만큼 쓴다. 1개면 1개다.

개수를 맞추려고 기준을 채워 넣지 마라. 그렇게 만들어진 기준이 정확히
이 스킬이 막으려는 "공허한 체크박스"다.

두 가지를 통과해야 한다.

**필요성** — 각 기준에 대해 "이게 깨지면 기능이 망가지는가?"를 묻는다.
아니면 지운다. "기존 테스트가 통과한다", "컨벤션을 따른다" 같은 것은
수용기준이 아니다. 앞의 것은 회귀 방어선이고 뒤의 것은 잡음이다.

**커버리지** — 범위의 `포함` 항목 중 어느 기준으로도 검증되지 않는 것이
있는가? 있으면 기준을 추가한다.

두 기준이 같은 검증 수단으로 검증된다면 사실 하나다. 합친다.

**기준이 8개를 넘으면** 계약서의 `분할하지 않는 이유` 칸을 채워야 한다.
**이 칸이 비어 있으면 FROZEN으로 전이할 수 없다.**
금지가 아니라 사람이 Gate 1에서 규모를 보게 하는 장치다.

### 근거와 출처 (추적성)

각 기준에 `근거`와 `출처`를 적는다. `출처` 값은 넷뿐이다.

| 값 | 뜻 | Gate 1에서 |
|---|---|---|
| `요구` | 사용자 요구 문장 원문 | 그대로 확인 |
| `상위` | 상위 동결 문서가 배정한 ID | 그 문서와 대조 |
| `리뷰` | 리뷰·검토에서 파생 | **`추론`과 같은 무게로 검토** |
| `추론` | 근거 없음 | 집중 검토 대상 |

`리뷰`와 `추론`이 이 표의 핵심이다. 둘 다 사용자가 요구한 적 없는 기준이므로
사람은 Gate 1에서 그 두 값의 행만 집중해서 보면 scope creep을 잡을 수 있다.

**리뷰에서 나온 기준을 `요구`로 적지 마라.** 근거를 지어내는 것과 같은 효과다.

## 검증 티어

| 티어 | 수단 | 판정 주체 |
|---|---|---|
| T1 | 이름 붙은 산출물을 부르는 단일 명령 | exit code |
| T2 | 재현 가능한 명령과 기대 출력 | 사람이 복붙해 재현 |
| T3 | 기록된 관찰 (스크린샷, 로그 파일) | 사람이 사후 검토 |
| T4 | 사람 육안 | 사람만 |

**기본값은 T1이다.** 강등하려면 계약서에 사유를 쓰고, 그 사유는 Gate 1에서
사람이 함께 승인한다. AI 단독 강등은 불가하다.

**"테스트 인프라가 없다"는 강등 사유가 아니다.** 그건 `신규테스트` 또는
`신규스크립트`를 만들라는 뜻이고, 무엇을 만들지는 Gate 1에서 사람에게 묻는다.
이걸 강등 사유로 허용하면 모든 기준이 T3·T4로 도망간다.

**T4가 하나라도 남으면 "완료"라고 말할 수 없다.**
T4 증거의 앵커는 이 파일 밖에 있어야 한다 — PR 코멘트 URL, 커밋 SHA, 이슈 링크.
같은 문서의 칸이 채워졌는지 보는 것은 사람 확인이 아니다.

## RED-first 규칙

T1/T2 기준은 구현 전에 실행해서 실패를 증거 로그에 남겨야 한다.
RED 로그가 없는 T1 기준은 **미충족으로 처리한다.**

**RED는 "예상한 이유"로 실패해야 한다.** import 에러, 문법 오류, 파일 없음으로
난 실패는 RED가 아니다. 그건 테스트가 아직 돌아가지도 않은 것이다.
기대한 assertion이 기대한 값으로 틀려야 진짜 RED다.

예외: 회귀 방어선 항목은 원래 통과해야 하므로 RED가 면제된다.

## 판정 출력 (고정 포맷)

**아래 수는 전부 수용기준 표에서 센 값이다. 표와 어긋나면 판정을 낼 수 없다.**

```
DoD VERDICT: <slug> @ <commit SHA>
  수용기준 표:     8개  (T1 5 · T2 1 · T3 1 · T4 1)
  T1/T2 자동:      6개 중 6개 PASS
  T3 기록 제출:    1개 중 1건
  T4 사람 확인:    1개 중 0건 완료, 1건 대기
  변경 요청:       2건
  => AWAITING_HUMAN
```

상태값:

- `VERIFIED` — 사람 확인 대기가 0건이고 자동 판정이 전부 PASS일 때만
- `AWAITING_HUMAN` — 자동은 통과했으나 사람 확인이 남음
- `FAILED` — 자동 판정에 실패가 있음
- `BLOCKED` — 검증 자체를 실행할 수 없음 (환경, 의존성 문제)

`AWAITING_HUMAN`일 때 "완료했습니다"라고 쓰지 마라. 남은 항목을 나열하라.

**판정 이후 커밋이 gate 결과를 바꾸면 증거 로그와 판정을 함께 갱신한다.**
판정이 가리키는 SHA와 브랜치 최종 SHA가 다르면 그 판정은 만료다.

## 자주 나오는 회피 패턴

| 회피 | 왜 안 되는지 |
|---|---|
| 검증 명령 칸에 grep·find 파이프라인을 적음 | 검증된 적 없는 프로그램이다. 식별자를 적을 수 없으면 T1이 아니다 |
| "기존 task가 없으니 T2로" | 강등 사유가 아니다. 무엇을 만들지 Gate 1에서 묻는다 |
| 기존 gate 조사를 건너뜀 | 이미 있는 architecture test를 못 보고 셸로 다시 짜게 된다 |
| `\|\|`·`&&`로 명령을 이어 붙임 | 조합의 exit code는 마지막 것이라 앞 실패를 삼킨다 |
| 판정 블록 수를 손으로 셈 | 표와 어긋난다. 표에서 도출하라 |
| 리뷰에서 나온 기준을 `요구`로 적음 | scope creep 탐지기가 죽는다 |
| T4를 문서 칸으로 자기 인증 | AI가 쓰는 파일이다. 앵커는 밖에 있어야 한다 |
| "일단 구현하고 기준은 나중에" | Gate 1 위반. 사후 기준은 구현에 맞춰 휘어진다 |
| 막히자 기준을 슬쩍 완화 | 규칙 3 위반. 멈추고 재승인받아라 |
| 항상 통과하는 테스트 작성 | RED가 없으면 그 테스트는 아무것도 증명하지 못한다 |
| 기준 9개인데 분할 사유 칸이 빔 | FROZEN 불가. 채우거나 나눠라 |
| "테스트는 통과했습니다" (안 돌리고) | 방금 실행한 출력만 증거다 |

## Red Flags — 멈추고 다시

- 검증 명령 칸에 `|`, `&&`, `!`, `$(` 가 보인다
- `검증 수단`에 식별자 대신 설명이 적혀 있다
- `기존 gate 조사` 칸이 비어 있다
- 기준이 8개를 넘는데 `분할하지 않는 이유`가 비어 있다
- 판정 블록의 수를 표에서 세지 않고 기억으로 적고 있다
- `출처`가 전부 `요구`다

## 다른 AI에서 쓰는 법

이 파일은 특정 도구에 의존하지 않는다. Claude Code와 Codex는
`~/.claude/skills/`, `~/.codex/skills/`에서 자동으로 발견한다.
그 밖의 환경에서는 이 파일 전체를 첫 메시지에 붙여넣으면 동일하게 동작한다.

**계약서 파일이 AI 간 인수인계 지점이다.** 다른 모델이 이어받을 때는
`docs/dod/<feature>.dod.md`만 읽으면 기준과 진행 상황을 모두 알 수 있다.
