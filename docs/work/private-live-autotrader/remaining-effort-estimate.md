## 0. 답과, 답하지 못하는 것

**답한다** — 코드 단위 3개(Phase 1·2·3)의 개발 소요. **약 1.2 ~ 6개월, 중앙 3.4개월.**

**답하지 못한다** — 프로그램 총 소요.

총 소요를 산출하지 못하는 것은 자료 부족이 아니라 **스펙의 구조 때문이다.** 일정을 지배하는 값
셋이 의도적으로 미정이다.

| 미정 값 | 위치 | 상태 |
|---|---|---|
| evidence 수집 기간 | §4.4 `ECG-4` | 미정 |
| canary 기간 | §5 Phase 3 "이 Phase가 선결정하지 않는 것" | 미정 |
| LIMITED 기간 | 〃 | 미정 |

미정인 이유가 문서에 있다 — §4.5 말미가 **"기간, 표본 수, coverage와 허용 손실 같은 정책값은
측정 결과를 보기 전에 사용자에게 승인받는다. 이 specification에는 근거 없는 기본 숫자를 고정하지
않는다"** 고 적었다. 빠뜨린 게 아니라 승인 대상으로 남겨 둔 것이다.

**그래서 이 산출의 결론은 숫자가 아니라 이것이다.**

> `NOGO-0` 승인과 evidence 기간 정책 승인은 분리할 수 없다. `NOGO-0` 원문이 이미 둘을 한 문장에
> 묶었다 — *"프로그램 개시 시 승인한 **비용·기간 상한이나 evidence 수집 기간의** 재평가 시점"*.
> evidence 기간을 모르는 채 기간 상한을 정하면, 그 상한을 evidence clock 하나가 단독으로 넘길 수
> 있다.

아래 §5의 민감도 표가 그 결합을 수치로 보인다.

## 1. 실측 기준선

완료된 실행 단위 셋을 git에서 측정했다.

| 단위 | 달력 | PR diff | outcome | 성격 |
|---|---|---|---|---|
| Master specification | 2026-07-20 ~ 08-01 (13일) | — | — | 리뷰 34라운드 |
| Phase 0 | 2026-08-02 ~ 08-26 (25일) | `#67` 83파일 · +8,954 −3,222 · 36커밋 | `P0-O1`~`O5` (5/42) | 프로세스를 **만들면서** 수행 · 리뷰 18라운드 |
| 거래 준비 | 2026-08-30 ~ 09-01 (3일) | `#72` 105파일 · +12,578 −24 · 66커밋 | `P3-O2`·`O3`·`O17` **부분** | 확립된 프로세스를 **소비** · 스펙 5R + 태스크 9회 + 최종 3R |

**측정한 것** — 달력 기간, 파일·라인·커밋 수, 리뷰 라운드 수.
**측정하지 않은 것** — 실제 작업 시간. 달력 기간에는 owner 응답 대기와 유휴가 섞여 있다.

거래 준비의 outcome 칸이 "부분"인 것이 중요하다. 그 단위의 `design.md` §5가 **"완전 충족이 아니며
각 outcome의 잔여는 Phase 3에 남는다"** 고 명시한다. 즉 3일에 outcome 3개를 **끝낸 것이 아니다.**

## 2. 처리량이 11.7배 달라졌다 — 그리고 지속 여부는 모른다

```
Phase 0      8,954줄 / 25일 =   358줄/일
거래 준비    12,578줄 /  3일 = 4,193줄/일        11.7배
```

같은 저장소, 같은 아키텍처 규칙, 같은 사람이다. 바뀐 것은 프로세스다. Phase 0의 25일에는
`feature-workflow`·subagent-driven-development·`definition-of-done`·리뷰 규율을 **만드는** 비용이
들어 있고, 거래 준비는 그것을 소비만 했다.

`#68` §1이 "실측은 이미 크다"며 비관적 근거로 든 것이 Phase 0(18라운드)과 master spec(34라운드)인데,
**둘 다 프로세스 확립 단위다.** 그 근거는 조건이 바뀐 지금 그대로 쓸 수 없다.

**다만 데이터점 하나로 속도를 세울 수는 없다.** 이 11.7배가 말하는 것은 "Phase 0 속도가 하한이
아니다" 뿐이다. 거래 준비에 유리했던 조건을 명시한다.

| 거래 준비의 조건 | Phase 3의 조건 |
|---|---|
| 범위가 좁고 스펙 리뷰 5라운드로 미리 좁혔다 | outcome 19개, 안전 계약이 얽혀 있다 |
| 새 아키텍처 결정이 없었다 — 기존 계층 위에 얹었다 | credential 경계 분리는 새 경계다 |
| 외부 의존이 없었다 — 주문 제출 없음, 실계정 없음 | 실 provider protocol, 실계정 reconcile |

**Phase 3은 셋 다 반대다.** 아래 추정에서 Phase 3에 더 큰 계수를 준 근거다.

## 3. 남은 9개 단위는 성격이 셋으로 갈린다

| 종류 | 단위 | 소요를 지배하는 것 | 추정 가능성 |
|---|---|---|---|
| **A. 코드** | Phase 1 · Phase 2 · Phase 3 | 개발 처리량 | 실측 2개로 범위 산출 |
| **B. 판정 게이트** | C · A1 · Z1 | owner 가용성, 증거 검토 | 며칠~2주 규모, 정밀 추정 무의미 |
| **C. 실계정 게이트** | A2 · A3 · A4 | 외부 기관·시장 조건·**미정 정책값** | **산출 불가** |

canary는 진입 기회가 생기는 시장 조건을 기다려야 하며, canary·LIMITED **기간 자체가 미정 정책값**이다.

## 4. 코드 단위 개발 소요

두 방식으로 계산하고 둘 다 적는다. 수렴하지 않으면 수렴하지 않는다고 적는다.

남은 software outcome은 `P1` 8 + `P2` 10 + `P3` 19 = **37개** (42개 중 88%).

### 방식 A — 볼륨 기준

측정된 outcome당 볼륨: Phase 0 `8,954/5 = 1,791줄`, 거래 준비 `12,578/3 = 4,193줄`(부분 충족 기준이라
완전 충족은 더 크다). 1,800~4,200줄로 잡으면 남은 볼륨은 **66,000 ~ 155,000줄**.

| 적용 속도 | 소요 |
|---|---|
| Phase 0 (358줄/일) | 184 ~ 433일 |
| 거래 준비 (4,193줄/일) | 16 ~ 37일 |

**16~433일. 27배 벌어져 이 방식만으로는 결정에 못 쓴다.** 라인 수가 노력의 나쁜 대리 변수인 탓이다.

### 방식 B — outcome당 일수 기준

스펙 자신의 작업 단위로 정규화한다. 측정값은 Phase 0 **5.0일/outcome**, 거래 준비 **1.0일/outcome**
(부분 충족).

Phase별로 계수를 다르게 준다. 근거는 §2의 조건 비교다.

| Phase | outcome | 계수 | 근거 | 소요 |
|---|---|---|---|---|
| Phase 1 | 8 | 2.0일 | 확립된 프로세스. 계약 정의가 많고 코드는 적다 | 16일 |
| Phase 2 | 10 | 2.5일 | Backtest·PAPER 두 실행 경로. 신규 코드 비중 큼 | 25일 |
| Phase 3 | 19 | 3.5일 | 새 경계·외부 의존·안전 계약 | 66.5일 |
| └ 거래 준비 선행분 | | | `P3-O2`·`O3`·`O17` 부분 충족 | −5일 |
| | **37** | | | **약 103일** |

### 두 방식의 교집합

방식 A `16~433일` ∩ 방식 B `37~185일`(계수 1.0~5.0 적용 시) = **37 ~ 185일**.

> **개발 경로: 약 1.2 ~ 6개월. 중앙 추정 3.4개월(103일).**

이 범위가 넓은 것은 데이터가 부족해서다. 데이터점이 둘뿐이고 그중 하나만 확립된 프로세스 위에서
측정됐다. **Phase 1을 끝내면 세 번째 데이터점이 생기고 그때 범위가 좁아진다.**

## 5. 지배항 — 병렬 구조가 총 소요를 결정한다

§5 roadmap이 evidence를 병렬로 돌린다. `P1-O1`(최소 수집 계약) 확정 시점에 분기해 software Phase와
동시에 진행하고, activation은 **둘 다** 도착해야 시작된다.

```
총 소요 = max(개발 경로, evidence 경로) + 활성화 사슬
```

- **개발 경로** = Phase 1 + 2 + 3 ≈ 103일 (37~185일)
- **evidence 경로** = `P1-O1` 확정(≈ 개발 시작 +20일) + collection readiness(≈ +10일) + **E**
- **활성화 사슬** = `ACT-1` + A2 + **canary C** + A4 + **LIMITED L** + Z1 ≈ 게이트 30~45일 + C + L

### 민감도

| evidence 기간 `E` | evidence 경로 | `max(개발 103일, evidence)` | + 게이트 30~45일 | 총 (C·L 제외) |
|---|---|---|---|---|
| 1개월 | 60일 | **103일** (개발 지배) | 133 ~ 148일 | 4.4 ~ 4.9개월 + C + L |
| 3개월 | 120일 | **120일** (비슷) | 150 ~ 165일 | 5.0 ~ 5.5개월 + C + L |
| 6개월 | 210일 | **210일** (evidence 지배) | 240 ~ 255일 | 8.0 ~ 8.5개월 + C + L |
| 12개월 | 390일 | **390일** (evidence 지배) | 420 ~ 435일 | 14.0 ~ 14.5개월 + C + L |

### 결정에 직결되는 관찰

**임계점은 `E ≈ 2.4개월`(73일)이다.** 그보다 길면 개발이 임계 경로에서 빠진다 — **개발을 아무리 빨리
해도 프로그램이 빨라지지 않는다.** 그 구간에서는 개발 속도 최적화에 자원을 더 쓰는 것이 일정에
기여하지 않는다.

역으로 `E`가 1개월 수준이면 개발이 지배하고, §4의 넓은 범위(1.2~6개월)가 그대로 총 소요의
불확실성이 된다.

**즉 `E`를 정하는 것이 일정 불확실성을 줄이는 첫 번째 수단이다.**

## 6. 비용 축

`NOGO-0`은 비용 상한도 요구한다. 축을 나열하되 값은 owner가 정한다.

| 축 | 성격 | 이 문서가 말할 수 있는 것 |
|---|---|---|
| 개발 비용 | 시간 비례 | §4·§5의 기간 추정에 비례. 지배항이 evidence면 개발 기간은 늘지 않는다 |
| 환경·보존 비용 (`ECG-3`) | **기간 비례, `E`에 직접 걸린다** | 장기 수집 host + storage를 `E` 동안 유지. `E`가 2배면 이 항목도 2배 |
| 실자본 | A2 이후 | owner 계정 규모가 상한. `ECO-5`가 배분 코리도(빗썸 비중 60~87.7%)를 정의했다 |
| 손실 허용 | 정책값 | §4.5가 "허용 손실"을 결과 보기 전 승인 대상으로 지정 |

**환경·보존 비용이 `E`에 직접 비례한다는 점이 중요하다.** 기간 상한과 비용 상한이 독립 변수가
아니다 — `E`를 늘리면 둘 다 늘어난다.

## 7. `NOGO-0` 승인에 필요한 입력

owner가 정해야 하는 값이다. §4.5 규칙에 따라 **측정 결과를 보기 전에** 승인해야 한다.

| # | 값 | 영향 |
|---|---|---|
| 1 | **evidence 수집 기간 `E`** | 일정·비용 양쪽의 지배항 (§5) |
| 2 | canary 기간 `C` | 총 소요에 직접 가산 |
| 3 | LIMITED 기간 `L` | 〃 |
| 4 | 실자본 규모 | 손실 노출 상한 |
| 5 | 환경·보존 비용 상한 (`ECG-3`) | `E`에 비례 |
| 6 | **비용 상한** | `NOGO-0` |
| 7 | **기간 상한** | `NOGO-0` |
| 8 | **재평가 시점** | `NOGO-0` — 상한 도달 전에 재평가할 지점 |

그리고 `#68` §1의 나머지 요구 — 상위 [`plan.md`](plan.md) §1 실행 단위 표에 **그 재평가를 소유하는
행**을 추가한다. 현재 traceability는 책임을 "Program 재평가"라고 적는데 그것은 등재된 실행 단위
이름이 아니다.

## 8. 이 산출의 한계

정직하게 적는다. 아래를 감안하지 않고 이 숫자를 쓰면 안 된다.

- **데이터점이 2개다.** 그중 확립된 프로세스 위에서 측정된 것은 1개(거래 준비)이고, 그마저 outcome
  부분 충족이다.
- **달력 기간 ≠ 작업 시간.** owner 응답 대기와 유휴가 섞여 있다. owner 가용성이 달라지면 달력
  기간도 달라진다.
- **outcome 난이도를 Phase 안에서 균일하게 가정했다.** 실제로는 `P3-O4`(실제 제출)와
  `P3-O10`(Web에서 LIVE 활성화 불가)의 난이도가 같지 않다.
- **라인 수는 노력의 나쁜 대리 변수다.** 방식 A를 교차 확인용으로만 쓴 이유다.
- **Phase 3의 조건이 거래 준비와 반대다**(§2). 계수 3.5일은 그 판단을 반영했지만 검증된 값이 아니다.
- **활성화 사슬의 게이트 소요 30~45일은 추정이다.** 실측 근거가 없다 — 거래소 승인 lead time과
  owner 가용성에 달렸다.

**범위를 좁히는 가장 값싼 수단은 Phase 1을 끝내는 것이다.** 세 번째 데이터점이 생기고, 그것이
확립된 프로세스 위의 **완전 충족** 단위라 계수를 검증한다.
