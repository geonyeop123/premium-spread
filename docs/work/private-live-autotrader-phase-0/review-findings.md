## 이 검토의 한계

- 기계 검증된 검토 레코드를 만들지 못했다. 검토자 산문이 도구의 65,536바이트 한도를 넘어 직렬화가 거부됐다. 판정 자체는 계약에 부합하지만 감사 레코드는 없고, 이 문서가 그 대체 기록이다.
- 구현 코드의 결함은 심사하지 않았다. `V15`·converter·행 잠금·신선도 유계·응답 스키마의 실제 구현 품질은 이 결과가 다루지 않는다.
- 상위 spec 본문(§2.5·§2.6 안전 불변식, §4.3 권한 표)의 품질은 심사하지 않았다.
- 18라운드 리뷰의 지적 원문은 읽지 않았다. 라운드별 대상 판정은 커밋 제목과 `dod.md` CR-1 구간 표에 의존한다.
- PR #67 에 GitHub 리뷰·코멘트가 0건이므로 이 이력은 전부 로컬 스펙 리뷰와 자체 gate 산물이다.

## 1. Phase 1 진입 전에 처리할 항목

### critical

**`NOGO-0` 에 상한값도 소유 실행 단위도 없다**

상위 `design.md` §9.4 는 "프로그램 개시 시 승인한 비용·기간 상한"에 도달하면 계속·축소·종결을 재평가하라고 요구하고, **상한값과 재평가 시점을 결과를 보기 전에 승인하라**고 못박는다. 그 상한값이 어느 문서에도 없다. 상위 `plan.md` §1 의 실행 단위 표 두 개에 `NOGO-0` 을 소유하는 행이 없고, §3 "결정하지 않는 것"에도 없어 위임된 것도 결정된 것도 아니다. traceability 는 책임을 "Program 재평가"라고 적는데 그건 등재된 실행 단위 이름이 아니다.

→ 상한값과 재평가 시점을 승인하고, 상위 `plan.md` §1 에 그 재평가를 소유하는 행을 추가한다. "결과를 보기 전에 승인"을 지킬 수 있는 마지막 시점이 Phase 1 진입 전이다.

### high — 순서와 상태

**`ACT-1` 시점이 문서끼리 어긋난다**

상위 `design.md` §4.5 는 `ACT-1` 을 "production credential 전에 평가"로 규정하고, 상위 `plan.md` A1 행은 진입 조건에 software 선행 조건을 걸지 않는다. 그런데 §5 흐름도는 Activation lane 을 `PRIVATE_LIVE_CODE_READY` 에서 시작해 `Candidate(ACT-1)` 으로 잇는다. 흐름도를 따르면 §1.2 자본 소진 제약 — 제품 실행 가능성의 전제 — 을 반증할 수 있는 가장 이른 시점이 Phase 2·3 의 outcome 29개를 만든 뒤로 밀린다. 전제가 거짓이면 전량 폐기되는 투자다.

→ 어느 해석이 정본인지 확정한다. `ECO-5` 산출값이 나오는 Phase 1 종료 직후로 당기고 그 평가에 GO/NO-GO 판정 권한을 준다. 현재 Phase 1 exit 점검은 산출값을 계산했는지만 보고 판정을 내리지 않는다.

**`FOUNDATION_ALIGNED` 가 merged 증거 없이 선언됐다**

상위 `design.md` §4.2 는 "software 축 전이는 해당 Phase DoD 의 merged 검증 결과로 선언한다"고 규정하고 §7.1 은 T2 를 "PR 및 merged `dev` Quality Gate"로 정의한다. PR #67 은 OPEN 인데 커밋 `963a5f9` 가 이미 DoD 를 `VERIFIED` 로 판정하고 `progress.md` 에 `FOUNDATION_ALIGNED` 를 append 했다. 미병합 브랜치에는 merged `dev` Quality Gate 가 존재할 수 없다.

→ PR #67 을 병합하고 merged `dev` 에서 gate 를 통과시킨 뒤 재선언하거나, 재계획으로 Phase 0 을 재배치하며 그 append 를 회수한다. 처리 근거를 `progress.md` 에 적어 선례를 남기지 않는다.

**남은 실행 단위 9개의 예상 소요를 다루는 산출물이 없다**

성공 경로는 software 4개 + gate 6개로 10개이고, 그중 6개가 코드 산출물이 아니다. A2·A3·A4 는 owner 의 실계정·실자금 투입 후에만 시작된다. 예상 소요를 다루는 서술이 어느 문서에도 없고 "결정하지 않는 것"에도 없다. 실측은 이미 크다 — software outcome 42개 중 12%를 소유한 Phase 0 이 리뷰 18라운드와 미병합 83파일 PR 을 소비했고, 그 앞 단위인 master specification 은 34라운드를 소비했다. 둘 다 코드 산출물이 없는 문서 단위다.

→ 실측을 기준선으로 남은 단위의 예상 소요를 산출하고 `NOGO-0` 상한 승인의 입력으로 쓴다.

## 3. 반복 지적의 인과 — 지적 44건 분류

`dod.md` 는 45건(critical 2·high 25·medium 18)으로 적지만 라운드 커밋 본문에서 실제로 세면 44건(critical 2·high 24·medium 18)이다. critical·medium 은 일치하고 high 가 1건 어긋난다.

### 위치별 지분

| 부류 | 건수 | 지분 | critical | high | medium |
|---|---:|---:|---:|---:|---:|
| **(b) 검사기 자체 로직 결함** | **23** | **52%** | **2** | 10 | 11 |
| (a) 도메인·동작 계약 결함 | 16 | 36% | 0 | 12 | 4 |
| (c) 문서 간 복제 불일치 | 5 | 11% | 0 | 2 | 3 |

critical 2건은 둘 다 검사기다 — 10R(`#` 주석이 줄바꿈을 삼켜 `DELETE FROM position` 통과)과 13R(`--1` 이 MySQL 산술식인데 주석 처리). 제품 계약에서는 critical 이 나오지 않았다.

44건 중 **32건(73%)** 이 직전 라운드 이후에 추가된 문장·검사 안에 있었다.

### 라운드별 수율

```
Phase 0 : 3 3 3 3 2 3 3 3 3 2 1 2 1 2 3 2 2 3     (18R, 하강 없음)
master  : 8 2 2 1 1 1 1 1 1 1 1 1 2 2 1 …1~2… 0 0  (34R, 수렴)
```

master spec 은 1R 8건에서 즉시 1~2건으로 떨어져 33·34R 연속 0으로 수렴했다. Phase 0 은 18라운드 내내 2~3건에서 평평하고 마지막 18R 이 3건으로 후반부 최고치다. 전반 9R 26건, 후반 9R 18건.

### 지분 순위

1. **검사기를 계약서가 소유한 구조** — 52%, critical 2건 전부. 10R~15R 구간 10건 중 9건이 검사기 로직. 6R~13R 커밋 8개가 `dod.md` 만 건드리며 같은 파서를 고쳤고 13R 에서 파서를 버릴 때까지 멈추지 않았다.
2. **리뷰 방식과 정지 규칙** — 지분을 직접 갖지 않지만 73%의 재발률과 평평한 수율 곡선이 기제다. 검사기 결함의 처방이 매번 더 큰 검사기였다.
3. **범위 구성** — (a) 16건 중 **11건이 D2 청산 스냅샷 + `V15` 묶음** 하나에서 나왔다. 16R~18R 만 보면 7건 중 6건. "표현 정렬이 전부"라고 선언한 Phase 에 스키마·동시성·신선도를 넣은 결정이 도메인 결함을 사실상 혼자 만들었다.
4. **문서 간 복제 소유** — 11%.

### 덧붙는 관찰

- 배포 중 Web 단절이 2R·4R·8R·10R 에 네 번 다시 제기됐다. 결론이 나지 않은 항목이 매 라운드 다시 계상되므로 44건 중 4건은 서로 다른 결함이 아니라 **하나의 미결 결정**이다. 접으면 실질 41건이고 (a) 는 13건으로 줄어 범위 구성의 지분이 더 내려간다.
- 검사기가 정당한 것을 막은 사례도 있다. 11R 에서 `DECIMAL(30, 10)` 의 타입 내부 콤마가 정상 `V15` 를 RED 로 만들었고, 12R 에서 유효한 `UPDATE position AS p` 가 거부됐다.

## 4. 후속

`definition-of-done` 스킬의 검사기 소유 구조는 별도로 수정했다 — 검증 수단을 이름 붙은 산출물로 고정하고, 기존 gate 조사를 Gate 1 필수로 두고, T1 검증 명령에서 셸 조합을 금지한다. 25회 대조 실험으로 확인했다 (`ai-skills` PR #5).

이 문서가 다루지 않는 것: 재계획안 자체. 재계획이 정당한지와 절차가 열려 있는지까지만 판정했고, 무엇을 어떻게 재배치할지는 결정하지 않았다.
