## 0. 이 단위의 성격

산출물이 코드가 아니라 문서다. 선례는 상위 [`plan.md`](../private-live-autotrader/plan.md) §2다 —
*"산출물은 코드가 아니라 문서이므로 `feature-workflow` ⑧ 구현은 문서 작성으로 대체되고 ⑨ 코드 리뷰는
문서 리뷰로 갈음한다."*

따라서 아키텍처 설계 항목은 전부 해당 없음이다. 빈 절을 만들지 않고 여기서 한 번에 닫는다.

| 항목 | 이 단위 |
|---|---|
| Facade·Controller 주입 경계 | 해당 없음 — 앱 코드 변경 0 |
| Domain port와 구현 모듈 | 해당 없음 |
| `MarketPair` identity 보존 경로 | 해당 없음 — 캐시 키·DB row·응답 없음 |
| 시간·범위 계약 (`Instant`, `[from,to)`) | 해당 없음 |
| DB·캐시 순서 | 해당 없음 |
| Flyway migration | 해당 없음 — schema 변경 0 |
| `JobExecutor` lock·lease·`JobResult` | 해당 없음 — 배치 없음 |
| 알림 event identity | 해당 없음 |
| `PublicEndpointPolicy`·`docs/runbooks/auth-security.md` | 해당 없음 — endpoint 변경 0 |

변경 대상은 두 갈래뿐이다. 이 디렉터리의 신규 문서와, 상위 [`plan.md`](../private-live-autotrader/plan.md)
§1·§3에 추가할 항목이다. 상위 `design.md`와 `dod.md`는 `FROZEN`이므로 읽기만 한다.

## 1. 푸는 문제

[`../private-live-autotrader-phase-0/review-findings.md`](../private-live-autotrader-phase-0/review-findings.md)
§1의 유일한 critical 원문이다.

> **`NOGO-0` 에 상한값도 소유 실행 단위도 없다**
>
> 상위 `design.md` §9.4 는 "프로그램 개시 시 승인한 비용·기간 상한"에 도달하면 계속·축소·종결을 재평가하라고
> 요구하고, **상한값과 재평가 시점을 결과를 보기 전에 승인하라**고 못박는다. 그 상한값이 어느 문서에도 없다.
> 상위 `plan.md` §1 의 실행 단위 표 두 개에 `NOGO-0` 을 소유하는 행이 없고, §3 "결정하지 않는 것"에도 없어
> 위임된 것도 결정된 것도 아니다. traceability 는 책임을 "Program 재평가"라고 적는데 그건 등재된 실행 단위
> 이름이 아니다.

지적이 셋으로 갈린다. 이 단위는 셋 다 다루되 서로 다른 방식으로 닫는다.

| # | 지적 | 이 단위가 하는 것 |
|---|---|---|
| 1 | 상한값과 재평가 시점이 없다 | **값을 정하지 않는다.** owner가 정할 수 있는 형태(§4 결정 입력표)를 만들고 근거를 붙인다 |
| 2 | 소유 실행 단위가 없다 | 상위 `plan.md` §1 gate 표에 `N0` 행을 추가한다. 내용 계약은 §8 |
| 3 | §3 "결정하지 않는 것"에도 없다 | 상위 `plan.md` §3에 위임 한 줄을 추가한다. §8.4 |

실제 편집은 [`plan.md`](plan.md)의 태스크가 수행한다.

`plan.md` §1 gate 표의 `Z2` 행이 이미 종결 트리거로 *"owner의 종결 트리거 발행 또는 `NOGO-0` 재평가 결과"*를
참조한다. **참조는 있는데 참조 대상이 등재돼 있지 않다.** §8의 `N0` 행이 그 대상이다.

## 2. 왜 지금인가 — Phase 1 진입이 차단된다

### 2.1 규칙 둘

상위 `design.md` §9.4:

> `NOGO-0` 프로그램 개시 시 승인한 비용·기간 상한이나 evidence 수집 기간의 재평가 시점에 도달하면
> 계속·축소·종결을 명시적으로 재평가한다. **상한값과 재평가 시점은 결과를 보기 전에 승인하며,** 재평가를
> 수행하지 않은 채 프로그램을 계속하지 않는다.

상위 `design.md` §4.5 말미:

> 기간, 표본 수, coverage와 허용 손실 같은 정책값은 **측정 결과를 보기 전에** 사용자에게 승인받는다. 이
> specification에는 근거 없는 기본 숫자를 고정하지 않는다.

같은 계약이 `PROM-3`에도 있다 — *"holdout 결과를 본 뒤 기준을 유리하게 바꾸는 것을 방지하기 위해 viability
policy를 평가 전에 승인한다."* §10은 *"평가 결과를 본 뒤 viability policy 변경"*을 재승인 대상으로 올린다.
세 조항이 보호하는 성질은 하나다 — **승인이 측정 결과에 오염되지 않을 것.**

### 2.2 지금은 그 성질이 아직 성립한다

| 사실 | 근거 |
|---|---|
| evidence collection = `COLLECTION_NOT_READY` | [`progress.md`](../../../.ai/planning/private-live-autotrader/progress.md) 상태 표 |
| 수집된 시장 데이터가 **0** | `progress.md` 2026-08-26 절 "로컬 named volume 부재, 운영·스테이징 환경 없음, OCI 인스턴스 미생성" |
| 장기 evidence clock 미시작 | 〃 · 상위 `design.md` §4.4 `ECG-4` |
| Phase 1 미진입 | `progress.md` "현재 Phase: `Phase 0 완료` · Phase 1 미진입" |

측정이 시작되지 않았으므로 볼 결과가 없다. **오염될 것이 없는 마지막 구간이다.**

### 2.3 Phase 1 진입이 그 구간을 닫는다

상위 `design.md` §4.4 말미와 `P1-O1`이 clock을 Phase 1의 **첫 산출물**에 건다.

> 장기 evidence clock은 이 프로그램에서 가장 긴 lead time 항목이다. 따라서 collection readiness는 Phase 1
> 전체 완료를 기다리지 않고 **최소 수집 계약(`P1-O1`)이 확정되어 배포 가능해지는 즉시** 평가하고 시작한다.

> `P1-O1` … 이 계약은 **Phase 1의 첫 산출물로 다루며 확정 즉시** §4.4의 collection readiness 평가 대상이 된다.

그리고 `ECG-4`가 *"실제 수집 시작 시점과 … 품질 정책을 기록하면 `COLLECTION_IN_PROGRESS`로 전이하고 **그때부터**
장기 evidence clock을 계산한다"*고 적는다.

```text
Phase 1 진입 ──► P1-O1 확정 ──► collection readiness 평가 ──► COLLECTION_IN_PROGRESS
                                                                   │
                                                          여기서부터 E 가 측정된다
                                                          = "결과를 보기 전" 이 끝난다
```

**판정.** `E`(evidence 수집 기간)를 포함한 8개 값의 승인은 `COLLECTION_IN_PROGRESS` 전에 끝나야 하고, 그
전이는 Phase 1의 **첫** 산출물에 달려 있다. 따라서 **`NOGO-0` 승인 없이 Phase 1에 진입하면 §9.4와 §4.5를
지킬 수 없다.** 이 단위가 닫히기 전까지 Phase 1 진입을 차단한다.

같은 판정을 `review-findings.md` §1이 이미 한 문장으로 적었다 — *"'결과를 보기 전에 승인'을 지킬 수 있는
마지막 시점이 Phase 1 진입 전이다."*

## 3. "프로그램 개시 시" 문면과 현실 — 판정 기록

### 3.1 사실관계

§9.4는 상한을 *"프로그램 개시 시 승인한"* 것으로 전제한다. 그 승인은 없었다.

| 시점 | 사건 | 상한 승인 |
|---|---|---|
| 2026-07-20 | 프로그램 개시 (master specification 착수) | 없음 |
| 2026-07-31 | 상위 `dod.md` `FROZEN`, specification `MASTER_SPEC_APPROVED` | 없음 |
| 2026-08-26 | Phase 0 종료 (`#67`) | 없음 |
| 2026-09-01 | 거래 준비 단위 종료 (`#72`) | 없음 |
| 현재 | Phase 1 진입 전 | **없음** |

[`remaining-effort-estimate.md`](../private-live-autotrader/remaining-effort-estimate.md) §1 기준으로 이미
소비한 달력은 master specification 13일 + Phase 0 25일 + 거래 준비 3일이다. **상한이 없는 상태로 그만큼
진행됐다.**

### 3.2 선택지와 채택

| 안 | 내용 | 비용 |
|---|---|---|
| A | 상위 `design.md` §9.4의 "프로그램 개시 시"를 "Phase 1 진입 전"으로 정정 | `FROZEN` 모체 문서 수정 → 상위 `dod.md` `## 변경 요청` + 재승인 + design.md를 대상으로 하는 기계 수용기준 재실행 |
| **C** | **문면을 고치지 않고, 이 문서에 판정을 근거와 함께 기록** | 문면과 현실의 차이가 문서에 남는다 |

**C안을 채택한다.** owner 승인 사항이다. 근거 넷.

1. **고쳐야 할 실질이 없다.** §9.4가 보호하는 성질은 §2.1이 정리한 "측정 결과에 오염되지 않은 승인"이고,
   그 성질은 evidence clock 미시작이므로 **지금도 성립한다.** 문면 수정은 실질을 바꾸지 않고 기록만 지운다.
2. **누락을 지우는 방향이다.** 승인이 빠진 채 프로그램이 진행됐다는 것은 사실이고, 이 프로그램의 기록 계약
   (`design.md` §4.2의 append-only 투영, `definition-of-done` 절대규칙 3 *"동결된 기준을 조용히 고치지 않는다"*)은
   사실을 남기는 쪽이다. 문면을 고치면 그 사실이 어느 문서에도 남지 않는다.
3. **완화가 아니라 강화다.** 이 판정은 §9.4를 느슨하게 하지 않는다. 오히려 §9.4에 없던 **더 좁은 시한**을
   부과한다 — "Phase 1 진입 전"(§2.3).
4. **반론은 `N0` 행이 흡수한다.** "문면을 두면 다음 재평가 때도 '개시 시'라는 잘못된 시점 표기가 남는다"는
   반론은 성립한다. 그 표기는 §8 `N0` 행의 **진입 상태 칸**이 회차별로 명시함으로써 해소된다. 문면은 최초
   승인의 이상적 시점을 말하고, `N0` 행은 실제 시점을 말한다.

### 3.3 이 판정이 만드는 의무

- 최초 승인의 기간 상한(#7)은 **기산점을 명시해야 한다.** 개시(2026-07-20)부터인지 승인 시점부터인지에 따라
  같은 숫자가 다른 뜻이 된다. §4 표의 각주가 이 요구를 소유한다.
- 이 판정은 상위 `design.md` §11의 수정 조건을 **발동시키지 않는다.** 모체 문서를 바꾸지 않기 때문이다.

## 4. owner 결정 입력표

[`remaining-effort-estimate.md`](../private-live-autotrader/remaining-effort-estimate.md) §7의 8개 항목과
**1:1로 대응하고 순서를 바꾸지 않는다.** 행을 더하거나 빼면 그 산출물과의 대응이 끊긴다.

**이 표는 승인값을 담지 않는다.** 표는 *무엇을 결정해야 하는가*만 고정한다. owner가 승인한 숫자와 승인
시각은 §7이 정한 대로 `progress.md`에 append한다. 그래서 이 문서는 owner 응답을 기다리지 않고 닫힌다 —

## 5. 8개 값의 의존 구조

독립 변수가 아니다. `E` 하나가 셋을 동시에 움직인다.

```text
                     ┌──────────────► #5 환경·보존 비용 상한   E 에 직접 정비례 (§6)
  #1 evidence 기간 E ─┼──────────────► #6 비용 상한            #5 를 통해
                     └──────────────► #7 기간 상한            지배항 전환 (§5 민감도)

  #2 canary C ─┐
               ├─────────────────────► #7 기간 상한            총계에 직접 가산. 값 미정이므로
  #3 LIMITED L ┘                                              상한의 포함 여부를 먼저 정해야 한다

  #4 실자본 ──────────────────────────► #6 비용 상한            상한이 거래 자본을 포함할 때만.
                                                              시간에 비례하지 않는 유일한 축

  #8 재평가 시점 ─────────────────────► 전부                   "상한 도달 전" 이므로 #6·#7 이
                                                              정해져야 의미를 갖는다
```

읽는 법 셋.

1. **`E`가 지배항이다.** `remaining-effort-estimate.md` §5 — 임계점 `E`≈2.4개월(73일). 그보다 길면 개발이
   임계 경로에서 빠지고 *"개발을 아무리 빨리 해도 프로그램이 빨라지지 않는다."* 그 구간에서 개발 속도에
   자원을 더 쓰는 것은 일정에 기여하지 않는다.
2. **기간 상한과 비용 상한은 따로 정할 수 없다.** 같은 문서 §6 — *"`E`를 늘리면 둘 다 늘어난다."* #7을
   느슨하게 잡으면 #6이 자동으로 커진다.
3. **`C`·`L`이 열려 있는 한 #7은 상한이 아니라 골격이다.** 각주 ③이 그 정의를 요구하는 이유다.

**총 소요를 다시 계산하지 않는다.** `remaining-effort-estimate.md` §0이 산출 불가를 선언했고 §8이 그 이유를
6개 한계로 명시했다. 이 문서는 인용만 한다.

## 6. 재평가 시점(#8)의 성격 — 반복 gate

`plan.md` §1 gate 표의 기존 행(`C`·`A1`~`A4`·`Z1`·`Z2`)은 전부 **1회성 전이**다. 진입 상태가 있고, 통과하면
상태축이 움직이고, 다시 오지 않는다.

`N0`는 셋 다 다르다.

| 성질 | 기존 gate 행 | `N0` |
|---|---|---|
| 횟수 | 1회 | **승인된 재평가 시점마다 반복** |
| 상태축 | 전이시킨다 | **전이시키지 않는다** (§7) |
| 결과 | 통과 / 차단 | **계속 · 축소 · 종결 세 갈래** |

세 갈래의 귀결.

- **계속** — 다음 재평가 시점을 기록하고 `progress.md`에 append한다. 상태축 변화 없음.
- **축소** — 축소가 상위 `design.md` §10 목록(범위·자본·notional·leverage·exposure·손실 범위 등)에 닿으면
  그 재승인 절차를 탄다. 닿지 않으면 8개 값의 갱신으로 끝난다.
- **종결** — `plan.md` §1 `Z2` 행으로 넘긴다. `Z2`가 이미 *"`NOGO-0` 재평가 결과"*를 진입 상태로 참조한다.

최초 1회는 **승인**이고 이후는 **재평가**다. 최초에는 도달할 상한 자체가 없으므로 §9.4의 "재평가 시점에
도달하면"이 발동하지 않는다. `N0` 행은 이 둘을 진입 상태 칸에서 구분한다(§8).

## 7. 종료 판정 — `progress.md` append

**새 상태축을 만들지 않는다.** owner 승인 사항이다.

상위 `design.md` §4.2가 이미 규정한다.

> specification, software, evidence collection, candidate/evidence, program 축의 현재값과 **승인 근거는
> `progress.md`가 소유한다.**

8개 값과 승인 시각은 **승인 근거**이지 상태값이 아니다. 기존 계약 안에서 처리된다. 새 축을 만들면 §4.2가
요구하는 초기값 정의와, 모체 `dod.md`의 축 초기값·비정형 상태 금지 수용기준까지 동결 계약을 건드리게 된다.

종료 조건은 하나다 — **`progress.md`에 다음이 append되면 이 단위는 종료한다.**

1. 8개 값 (또는 회차의 계속·축소·종결 판정)
2. 승인 시각
3. 다음 재평가 시점 (계속인 경우)

§4.2의 *"주문 권한에 영향을 주는 값은 runtime durable control state에 versioned effective input으로 먼저
commit"* 요구는 **이 append에 걸리지 않는다.** activation이 `ACTIVATION_NOT_STARTED`이고 runtime durable
control state 자체가 아직 존재하지 않는(Phase 3 산출물) 시점이며, 8개 값은 상태축 값이 아니다. 재평가
결과가 **종결**이고 그 시점에 주문 권한이 존재한다면 그때는 `Z2`가 §4.2·§4.3 경로를 소유한다.

## 8. 상위 `plan.md`에 추가할 내용 계약

**실제 편집은 [`plan.md`](plan.md)의 태스크다.** 여기서는 계약만 고정한다.

### 8.1 `N0` 행의 위치

gate 표(`C`·`A1`~`A4`·`Z1`·`Z2`)의 **`C` 행 앞**, 즉 표의 첫 행이다. 근거 둘.

- `C`(Collection 시작)의 진입 조건이 `P1-O1` 확정이고, §2.3이 그 지점을 "결과를 보기 전"의 끝으로 판정했다.
  `N0`는 그보다 앞에서 끝나야 한다. 표의 순서가 그 선후를 드러낸다.
- Phase 표가 아니라 gate 표다. 코드 산출물이 없고 전이 선언 권한이 owner에게 있는 행이므로 gate 표가 맞다.

### 8.2 `N0` 행의 내용

gate 표의 열은 `#` · 실행 단위 · 진입 상태 · owner · 산출물 · 종료 판정이다. 각 칸이 담아야 하는 것.

| 열 | 계약 |
|---|---|
| `#` | `N0` |
| 실행 단위 | **`Program 재평가 (NOGO-0)`** 를 포함하고, 같은 칸에 **반복 gate**임을 적는다 |
| 진입 상태 | 최초와 이후를 구분한다. 최초는 *Phase 1 진입 전이며 evidence collection이 `COLLECTION_NOT_READY`*, 이후는 *승인된 재평가 시점 도달마다* |
| owner | `owner` |
| 산출물 | 이 디렉터리의 결정 입력 8개에 대한 승인값과 승인 시각, 회차의 계속·축소·종결 판정 |
| 종료 판정 | **상태축 전이 없음** — `progress.md` append로 종료. 종결 판정이면 `Z2`로 넘긴다 |

**실행 단위 이름을 `Program 재평가`로 고정하는 이유.** 상위 `design.md` §8 traceability가 `NOGO-0`의 책임을
`Program 재평가`라고 적었고, `review-findings.md`가 *"그건 등재된 실행 단위 이름이 아니다"*라고 지적했다.
같은 문자열을 실행 단위 이름으로 채택하면 **모체 `FROZEN` 문서를 고치지 않고** 그 지적이 닫힌다.

### 8.3 표 아래에 추가할 설명

표 뒤 본문에 한 문단을 덧붙인다. 담을 것 셋.

- `N0`만 반복 gate이고 나머지 행은 1회성 전이라는 것 (§6의 성질 표).
- `Z2` 행이 참조하는 *"`NOGO-0` 재평가 결과"*의 소유 행이 `N0`라는 것.
- 재평가 회차마다 `progress.md` append와 함께 §11의 검증 러너를 실행한 결과를 남긴다는 것.

### 8.4 §3에도 한 줄을 추가한다

`plan.md` §3 "이 plan이 결정하지 않는 것"은 **미결정 목록이 아니라 위임 등기부**다. 현재 네 항목 중 셋이
"— 누가 소유한다"를 함께 적는다.

> - Phase별 PR 개수와 순서 — `design.md` §6.2가 Phase agent에 위임한다
> - 장기 증거 수집의 환경·비용 선택 — `design.md` §4.4의 gate가 소유한다
> - activation 정책값(기간, 표본 수, 허용 손실) — `design.md` §4.5가 사용자 승인으로 고정한다

따라서 `NOGO-0`을 §3에 넣는 것은 §1 표와 모순되지 않는다. **§1은 누가 소유하는지를, §3은 이 plan이 값을
정하지 않는다는 것을 적는다.** `review-findings.md`가 *"§1에 소유 행이 없고 §3에도 없어 위임된 것도 결정된
것도 아니다"*라고 둘을 함께 든 이유가 이것이다 — 한쪽만 채우면 지적의 절반이 남는다.

넷째 항목이 이미 "activation 정책값(기간, 표본 수, 허용 손실)"을 담고 있어 `C`·`L`과 허용 손실은 부분적으로
덮이지만, **비용·기간 상한과 재평가 시점은 activation 정책값이 아니라 프로그램 거버넌스 값이라 덮이지
않는다.** 그래서 별도 항목이 필요하다.

### 8.5 모체 `design.md`·`dod.md`는 건드리지 않는다

상위 `plan.md`는 모체 `dod.md`가 동결한 대상이 아니다. 다만 모체 `dod.md` `AC4`가
`docs/work/private-live-autotrader/*.md`의 **상대 링크가 모두 실재 파일을 가리키는지** 검사하므로, `N0` 행이
이 디렉터리를 링크하면 그 검사를 다시 통과시켜야 한다. [`plan.md`](plan.md)의 해당 태스크가 그 재실행을
포함한다.

## 9. 이 단위가 결정하지 않는 것

- **8개 값 자체.** owner 결정이다. 이 단위는 결정 가능한 형태를 만드는 데서 끝난다.
- **프로그램 총 소요.** `remaining-effort-estimate.md` §0이 산출 불가를 선언했고 §8이 6개 한계로 이유를
  적었다. 다시 계산하지 않는다.
- **`C`·`L`의 범위.** 상위 `design.md` §5 Phase 3이 명시적으로 비워 둔 값이다. 근거 없이 채우지 않는다.
- **허용 손실이 `NOGO-0` 입력인가.** 두 산출물이 갈린다(§4 각주 ④). owner가 ⑦에서 판정한다.
- **`ACT-1` 평가 시점.** [`act1-evaluation-timing.md`](../private-live-autotrader/act1-evaluation-timing.md)
  §7의 owner 결정 3건이 소유한다. #8의 후보 (b)가 그 결정에 의존한다는 사실만 기록한다.
- **상위 `design.md` §9.4의 문면.** §3의 C안에 따라 고치지 않는다.
- **`remaining-effort-estimate.md` §7 목록의 수정.** `[DECISION_NEEDED-4]`가 편입으로 결정되면 필요해지지만
  이 단위의 범위가 아니다.
- **환경·보존 비용의 절대 금액과 host·storage 선택.** `ECG-1`~`ECG-3`(Collection readiness gate, `plan.md`
  §1 `C` 행)이 소유한다.

## 11. 검증 전략

수용기준의 정본은 [`dod.md`](dod.md)이고 실행 러너는 `verify.sh`다. 여기서는 어느 계층에서 무엇을 보는지만
고정한다.

| 검증 대상 | 계층 | 수단 |
|---|---|---|
| 결정 입력표가 **결정 가능한 형태**인가 (8행 1:1·동순, 단위·권고·근거 완비) | 이 디렉터리 `design.md` ↔ `remaining-effort-estimate.md` §7 | `verify.sh check decision-inputs` |
| 새 상태 이름을 도입하지 않았는가 | 이 디렉터리 `*.md` ↔ 참조 코퍼스 4종 (모체 `design.md`, `definition-of-done` 스킬 2종, phase-0 러너의 판정 어휘) | `verify.sh check state-vocabulary` |
| `N0` 행이 `C` 앞에 있고 반복 gate임이 행 안에 있는가, §3에 위임 항목이 있는가 | 상위 `plan.md` §1·§3 | `verify.sh check owner-row` |
| 모체 `FROZEN` 산출물 2종이 변경되지 않았는가 | 저장소 | `git diff --quiet` |
| 상위 `plan.md`의 상대 링크가 실재하는가 (모체 `AC4` 회귀) | 저장소 | `verify.sh check master-links` |
| 정본 문서 무결성 | 저장소 | `bash docs/check-documentation.sh` (회귀 방어선) |
| 하네스 무결성 | 저장소 | `bash docs/check-harness.sh` (회귀 방어선) |
| 8개 값의 승인 | owner | 사람 확인 (T4) — 이 단위는 `AWAITING_HUMAN`으로 남는다 |

**값이 채워졌는지는 수용기준이 아니다.** 그것을 수용기준으로 두면 owner 응답 없이 이 단위가 영원히 닫히지
않는다. 수용기준은 "값을 채울 수 있는 형태가 갖춰졌다"이고, owner 승인은 `AWAITING_HUMAN` 항목 하나로만
남는다.
